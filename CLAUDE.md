## Стек
- Python 3.12+, FastAPI, uvicorn; `uv` — для разработки. Регламент только рекомендует 3.10+, поэтому берём новый Python; в README требование — 3.12+.
- Хранилище обязательной части — in-memory под одним `threading.Lock`: запуск без Docker и без внешних сервисов. Redis — только бонус через Docker Compose, включается env `REDIS_URL`; без него — in-memory.
- Uvicorn — ровно 1 worker: lock и состояние живут в одном процессе.
- Эндпоинты — `def`, не `async def`: `threading.Lock` в `async def` заблокирует event loop.
- Время — только через одну функцию `now()` в `app/otp.py`; в тестах её подменяем, `sleep` на 120 с не пишем.
- LLM не используем: в ТЗ 6 он не нужен, а ключа у жюри нет.
- Дашборд (бонус) — один статический `app/static/dashboard.html` без сборки, его отдаёт FastAPI. React и Node не нужны.
- `OTP_SECRET` (ключ HMAC) — из env; не задан → генерируется при старте (`secrets.token_bytes(32)`).

## Идея
- Задание: ТЗ 6 «OTP-сервис», осенний хакатон INAI 2026, тема «Умная и безопасная связь».
- Решение одной фразой: REST API выдачи и проверки одноразовых кодов, которое выдерживает перебор и спам.
- Wow-момент (жюри — технари): `attack.py` вживую упирается в защиту; из 20 параллельных `verify` одним кодом успешен ровно один; хранится только HMAC.
- Демо (3 мин):
  1. `send` → код в консоли → `verify` → 200; повторный `verify` тем же кодом → 401.
  2. 5 неверных вводов → 423, номер заблокирован на 15 мин.
  3. `attack.py`: перебор по одному номеру и по 50 номерам с одного IP — обе атаки остановлены.
  4. Параллельные `verify` одним кодом — 200 ровно у одного.
  5. Бонус: дашборд событий безопасности.

## Контракт

### API
| Метод | Путь | Вход | Выход |
|---|---|---|---|
| POST | `/otp/send` | `{"msisdn": str}` | 200 / 429 (+ `Retry-After`) |
| POST | `/otp/verify` | `{"msisdn": str, "code": str}` | 200 / 401 / 410 / 423 / 429 |
| GET | `/events` | — | последние события безопасности (для дашборда) |

Тело ответа — `{"detail": "<причина>"}`. Невалидное тело запроса → 422 (стандарт FastAPI).

### Требования ТЗ
- Код — 6 цифр из `secrets.randbelow(10**6)`, с ведущими нулями. TTL 120 с, одноразовый; новый `send` аннулирует предыдущий код.
- Хранится только `hmac.new(OTP_SECRET, msisdn + code, sha256)`; сравнение — `hmac.compare_digest`.
- `send`: задержка перед повторной отправкой — 30 / 60 / 120 с (после 1-го / 2-го / 3-го `send`); не больше 3 `send` на номер за 10 мин (скользящее окно).
- `verify`: после 5 неверных вводов номер блокируется на 15 мин; не больше 20 `verify` в минуту с одного IP по всем номерам.
- Параллельные `verify` одним верным кодом → 200 ровно у одного: проверка и пометка «использован» — под одним lock.
- Журнал безопасности: выдача, неверный ввод, блокировка, срабатывание лимита — без кодов. JSON lines в `security.log` + последние события в памяти для `/events`.
- Доставка кода: строка `OTP <msisdn> <code>` в stdout и в `otp.log`.

### Наши трактовки (ТЗ их не задаёт; дублируются в README)
- Порядок проверок в `verify`: 429 (лимит по IP) → 423 (номер заблокирован) → 401 (нет активного кода или он уже использован) → 410 (истёк) → 401 (неверный код).
- Каждый 401 увеличивает счётчик неверных вводов номера. Счётчик сбрасывается при успешном `verify` и по окончании блокировки; новый `send` его не сбрасывает.
- `send` для заблокированного номера → 429: у `send` в ТЗ только 200 и 429.
- IP клиента — `request.client.host`. `X-Forwarded-For` не доверяем: иначе атакующий подменит IP.
- Тайминги и лимиты — из env (дефолты = ТЗ), чтобы жюри могло ускорить сценарии.
