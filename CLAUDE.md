## Стек
- Python 3.12+, FastAPI, uvicorn; `uv` — для разработки. Регламент только рекомендует 3.10+, поэтому берём новый Python; в README требование — 3.12+.
- Хранилище обязательной части — in-memory под одним `threading.Lock`: запуск без Docker и без внешних сервисов. Redis — только бонус через Docker Compose, включается env `REDIS_URL`; без него — in-memory.
- Uvicorn — ровно 1 worker: lock и состояние живут в одном процессе.
- Эндпоинты — `def`, не `async def`: `threading.Lock` в `async def` заблокирует event loop.
- Время — только через одну функцию `now()` в `app/otp.py`; в тестах её подменяем, `sleep` на 120 с не пишем.
- LLM не используем: в ТЗ 6 он не нужен, а ключа у жюри нет.
- Дашборд (бонус) и `/demo` — статические `app/static/dashboard.html`, `app/static/demo.html` без сборки, его отдаёт FastAPI. React и Node не нужны.
- `OTP_SECRET` (ключ HMAC) — из env; не задан → генерируется при старте (`secrets.token_bytes(32)`).

## Идея
- Задание: ТЗ 6 «OTP-сервис», осенний хакатон INAI 2026, тема «Умная и безопасная связь».
- Новые правила демо (жюри, 20.11 19:45): обязательные пункты остаются, но для 10 баллов за демо нужны идея продукта, пользователь и осмысленное применение.
- Продукт: вход по SMS для малого бизнеса в Кыргызстане, который не боится ботов.
- Пользователи: небольшие сервисы со входом по номеру телефона (доставка, магазин, запись к врачу) и их владелец.
- Проблема: (1) перебор кода → захват аккаунта; (2) SMS pumping — боты массово дёргают `send`, бизнес платит за тысячи SMS.
- Решение одной фразой: OTP-сервис, который отбивает перебор и не даёт ботам сжечь бюджет на SMS — и показывает владельцу, сколько денег это сэкономило.
- Что добавляем к обязательной части:
  - `demo.html` (`/demo`) — вход в выдуманный сервис доставки через `send` / `verify`.
  - Дашборд: события + «отбито попыток перебора» и «сэкономлено N сом» = отклонённые `send` × `SMS_PRICE_SOM` (env).
  - Лимит `send` по IP против pumping по многим номерам — только за env-флагом, по умолчанию выключен (иначе скрытые сценарии жюри с `send` на разные номера с одного IP получат лишний 429).
- В жизни: вместо `outbox/sms.jsonl` — SMSC оператора по SMPP; остальная логика та же.
- На демо (VM): `sms_gateway` читает outbox и шлёт код в Telegram (@otp_shield_bot) тому, кто привязал номер, поделившись своим контактом. Сервис outbox не читает, HTTP-метода для кода нет. Непривязанные номера — только outbox.
- Wow-момент (жюри — технари): `attack.py` вживую упирается в защиту, счётчик «сэкономлено» растёт; из 20 параллельных `verify` одним кодом успешен ровно один; хранится только HMAC.
- Демо (3 мин):
  1. Кто пользователи и какая проблема — 20 с.
  2. Вход на `/demo`: код из `outbox/sms.jsonl` («пришло на телефон») → 200; повтор тем же кодом → 401.
  3. `attack.py`: перебор кода (5 ошибок → 423) и SMS pumping по 50 номерам — обе атаки гаснут на дашборде, «сэкономлено N сом» растёт.
  4. Параллельные `verify` одним кодом — 200 ровно у одного; в хранилище только HMAC.

## Контракт
Источник — ТЗ (`TASKS_ORIGINAL_RU.docx`) и уточнения v1.1 (`CLARIFICATIONS_RU.md` §6) из `INAI_2026_participants_v1.1.zip`; при расхождении правы уточнения. Открытые сценарии жюри — `06_otp/scenarios_examples.json` (O01, O03, O07, O12, O16), фикстура — `06_otp/test_identities.json` (50 номеров, IP `192.0.2.10`, `198.51.100.20`).

### API
| Метод | Путь | Вход | Выход |
|---|---|---|---|
| POST | `/otp/send` | `{"msisdn": str}` | 200 / 400 / 423 / 429 (+ `Retry-After`) / 503 |
| POST | `/otp/verify` | `{"msisdn": str, "code": str}` | 200 / 400 / 401 / 410 / 423 / 429 |
| GET | `/events` | — | последние события безопасности (для дашборда) |
| GET | `/stats` | — | `{"counts": {тип: N}, "saved_som": float}` — счётчики событий с запуска (in-memory, обнуляются при рестарте) и сумма `saved_som` отклонённых `send` |

Тело ответа — `{"detail": "<причина>"}`. Некорректный JSON или формат → **400**, не 422: стандартную ошибку валидации FastAPI переопределяем.

### Требования ТЗ и уточнений
- Формат: `msisdn` — строка ровно из 12 цифр, начинается с `996`; `code` — строка ровно из 6 цифр, ведущие нули сохраняются, `000000` допустим.
- Код — `f"{secrets.randbelow(10**6):06d}"`. Одноразовый; новый успешный `send` аннулирует предыдущий код, отказ `send` (429/423) действующий код не трогает.
- Истечение: `elapsed >= 120` с → 410 (ровно на 120 с уже 410).
- Хранится только `hmac.new(OTP_SECRET, msisdn + code, sha256)`; сравнение — `hmac.compare_digest`.
- `send`: успешные выдачи в окне `(t−600, t]` нумеруются 1, 2, 3. Между 1-й и 2-й — не меньше 30 с, между 2-й и 3-й — 60 с; после 3-й — 120 с, но 4-я запрещена, пока в окне 3 выдачи → 429. Окно опустело → ступень задержки сбрасывается.
- `verify`: неверный код при активном OTP → 401 и +1 к счётчику; 5-я такая ошибка сразу отвечает **423**, блокировка `[t, t+900)`. Во время блокировки `verify` (и с верным кодом) → 423, `send` → **423**.
- Счётчик не увеличивают: отсутствующий, использованный или истёкший код, ошибка формата.
- IP-лимит: 20 `verify` в окне `(t−60, t]` с одного IP по всем номерам, 21-й → 429; ровно 20 проходят (O16 — 20 параллельных с одного IP). Учитывается любой `verify`, в том числе 400. Проверяется первым — до формата кода и блокировки номера.
- `send` для заблокированного номера → 423, даже если не прошла задержка (O12: второй `send` через 0 с → 423, не 429).
- Время — float-секунды (O07: на 29.999 с ещё 429); границы окон — строго как выше.
- Параллельные `verify` одним верным кодом → 200 ровно у одного, остальные 401 (O16: 1×200, 19×401): проверка и пометка «использован» — под одним lock.
- Журнал безопасности: выдача, неверный ввод, блокировка, срабатывание лимита — без кодов. JSON lines в `security.log` + последние события в памяти для `/events`.
- Доставка «SMS»: каждая выдача дописывается строкой JSON `{"ts": "2026-11-21T09:00:00+06:00", "msisdn": "996770730000", "code": "012345"}` в `outbox/sms.jsonl` **в корне репозитория** (не в `backend/`; путь — env `OTP_OUTBOX`). Сервис этот файл не читает. Жюри берёт последнюю строку для номера. Публичного HTTP-метода получения кода нет. В stdout и прочие логи код не пишем.

### Наши трактовки (уточнения их не задают; дублируются в README)
- Порядок проверок в `verify`: 429 (лимит по IP) → 400 (формат) → 423 (номер заблокирован) → 401 (нет активного кода или он уже использован) → 410 (истёк) → 401 (неверный код; на 5-й — 423).
- Порядок проверок в `send`: 400 (формат) → 423 (номер заблокирован) → 429 (задержка или 3 выдачи в окне).
- Отказы 429 в окно IP-лимита не попадают: атакующий получает ровно 20 `verify` в минуту.
- Истёкший код остаётся до нового `send`: повторный `verify` снова → 410.
- Блокировка аннулирует активный код.
- Счётчик ошибок привязан к номеру, не к OTP (иначе `send` между попытками обнуляет защиту): сбрасывается при успешном `verify` и по окончании блокировки; новый `send` его не сбрасывает.
- `Retry-After` (целые секунды, вверх) — у 429 и 423 в `send`: до ближайшего разрешённого `send` или до конца блокировки.
- `ts` в outbox — из `now()` в `+06:00` (Asia/Bishkek). Путь outbox по умолчанию считается от `__file__`, не от cwd.
- `msisdn` или `code` не строкой (например, числом в JSON) → 400.
- IP клиента — `request.client.host`: IP соединения. `X-Forwarded-For` не принимается: команда запуска из README — с `--no-proxy-headers` (дефолт uvicorn верит XFF с `127.0.0.1`, а стенд ходит именно оттуда — перебор с подменой XFF обошёл бы IP-лимит). На VM `--proxy-headers` включён только в prod-compose за Caddy.
- Сбой канала доставки (запись в outbox) → `send` 503: код и выдача не сохраняются, действующий код не трогается, повтор сразу возможен. Redis недоступен → 503 на любой запрос.
- Глубоко вложенный JSON → 400, как любой некорректный JSON. В журнал при 429 по IP `msisdn` попадает, только если он корректного формата.
- Некорректные значения env (не число, отрицательное, дробный лимит, `SEND_MAX=0`) и `REDIS_URL` без `OTP_SECRET`/`OTP_SECRET_FILE` → сервис не стартует с понятной ошибкой.
- Тайминги и лимиты — из env (дефолты = ТЗ), чтобы жюри могло ускорить сценарии.
- Лимит `send` по IP (против SMS pumping) — env `SEND_IP_MAX` (успешных выдач с IP в окне `SEND_IP_WINDOW`, дефолт 600 с); `0` = выключен, это дефолт. Включён → после 429 по номеру проверяется 429 по IP (+ `Retry-After`).
- Отклонённые `send` (423, 429) пишутся в события с `saved_som` = `SMS_PRICE_SOM` (env, дефолт 1.04 — минимальная официальная цена SMS Beeline KG): дашборд суммирует «сэкономлено не меньше N сом».
- Номер, к которому не обращались 24 ч (`max(SEND_WINDOW, OTP_TTL, LOCK_SECONDS, 86400)`), забывается целиком (в том числе счётчик ошибок и истёкший код) — одинаково в памяти и в Redis. Внутри этого срока поведение не меняется: истёкший код отвечает 410.
- Redis (бонус, `REDIS_URL`): HMAC-ключ — env `OTP_SECRET` или файл `OTP_SECRET_FILE` (создаётся при первом старте), не в Redis.
- Сценарии в `scenarios_examples.json` — примеры: сброс состояния между сценариями обеспечивает стенд жюри; `client_ip` и `advance` — см. «Стенд жюри».

### Стенд жюри (уточнение жюри, 20.11 ~23:00)
- Сервис запускают локально на Linux, командой из README.
- Скрипт подключается с двух адресов — `127.0.0.1` и `127.0.0.2`; IP — из самого подключения, `X-Forwarded-For` не шлют. IP из JSON (`192.0.2.10`, `198.51.100.20`) — только примеры, в коде их не прописываем.

- OTP жюри берёт из `outbox/sms.jsonl` по пути из README; другой путь — указать в инструкции запуска.

### Интерфейс для тестов (A реализует, B пишет тесты по нему)
- Время: `monkeypatch.setattr("app.otp.now", lambda: t)`; `now()` → float-секунды (Unix time).
- Сброс: `app.otp.reset()` очищает хранилище, счётчики, лимиты и события — в autouse-фикстуре.
- Outbox: env `OTP_OUTBOX` читается при каждой записи → в тесте `monkeypatch.setenv("OTP_OUTBOX", str(tmp_path / "sms.jsonl"))`; код — последняя строка для номера.
- IP клиента: `TestClient(app, client=("192.0.2.10", 50000))` → `request.client.host == "192.0.2.10"`.
